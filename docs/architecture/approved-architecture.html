Code Along · Approved architecture · 13 November 2026

Code Along application architecture

Build an independently authored, learning-focused collaborative Python platform: a React/TypeScript frontend, a Django product backend, a small Node/Yjs collaboration service, PostgreSQL durability, and an isolated browser execution application. Start with browser practice and instructor assessment; add trusted server grading only behind a separate execution-security gate.

Status: architecture approved by the project owner on 13 November 2026. This document records the accepted design and milestone scope; approval does not establish that its integrations have passed testing. Implementation proceeds one verified unit at a time, with separate approval before every commit. Architecture changes require approval.

This design uses the source investigation and runtime investigation. PyTogether demonstrated the core experience, but also exposed weak authorization, limited persistence, misleading save/execution states and a partial final document in one rapid interaction whose cause remains unresolved. Code Along needs explicit contracts and regression tests; changing a library alone does not prove that those problems are solved.

Working assumptions: browser-first, desktop-first coding with responsive reading/review; small study groups and classrooms; one deployment region initially; individual and team projects; Python is the only execution language. An initial validation target is 2–6 simultaneous editors per project and a 30-learner workspace. These are proposed test loads, not measured capacity or guaranteed limits. Institution hierarchy, billing, native desktop apps and AI tutoring are outside the first release.

4. Backend architecture

Django is the single authority for product policy. Its apps are accounts, workspaces, projects, collaboration access, messaging, learning, submissions, execution control and audit. HTTP views/serializers adapt requests; selectors perform scoped reads; services implement transactional writes; policies answer named actions against authenticated actors and authoritative object relationships. Use ordinary Django models directly rather than placing a generic repository abstraction over every table.

The Node service owns live CRDT instances and may write only collaboration-state/checkpoint tables through a restricted database role. Django owns their schema/migrations and file/project permissions. Node receives authoritative admission/lease decisions through a private API; it does not invent an alternate role policy. This creates one deliberately narrow service boundary instead of decomposing every feature into a service.

6. Real-time architecture and durability contract

Two channels, different ownership: Hocuspocus/Yjs handles document sync and awareness through /collab. A separate Channels socket at /events carries chat notifications, file-tree/permission changes and submission/job updates. This keeps document protocol changes out of product-event handlers. Use one multiplexed provider connection for the small project's document subscriptions where supported, rather than a new TCP connection per file. File tree/path/permissions remain REST-owned metadata, not an editable Y.Map that could grant access.

One Y.Doc per text file, addressed by immutable document ID and generation. Small first-release projects load their bounded text-document set before a multi-file Run snapshot; only the active document has an EditorView. A board is a separate persisted document, so drawing points do not consume the text-file budget or lose durability when text is saved.

6.1 Admission, editing and reconnect

  1. Browser requests a narrow one-use collaboration ticket from the authenticated API using CSRF protection. Issue a fresh ticket for each document subscription/reauthentication, even when providers share one transport; never reuse a consumed ticket across files.
  2. Provider sends the ticket in its authentication exchange, not a query string. Node asks the private authorization API to validate session, project/file association, generation and allowed actions.
  3. On first use, one room owner atomically initializes the binary document from an immutable starter exactly once. Later joins load the persisted binary state; no normal reconnect recreates a CRDT from plaintext.
  4. Standard Yjs sync reconciles changes. Validate schema, size, rate and read-only scope before applying messages. Reject invalid updates without advertising them as accepted.
  5. Reconnect obtains new authorization, loads canonical state and reconciles pending local updates. A stale generation or revoked permission cannot resurrect a deleted/replaced document; offer an authorized recovery/export path for local work.

Binary persistence is important: Hocuspocus documents that rebuilding Yjs documents from JSON can cause merging/duplication problems. Its existing persistence hooks are useful, but Code Along must implement its own durability meaning. Hocuspocus persistence.

6.2 Saved means a committed checkpoint

Realtime peer delivery is allowed before a database checkpoint completes. The UI must say Pending/Saving during that interval. Hocuspocus's synced event and debounced store hook are not a PostgreSQL commit receipt. Do not promise zero loss of unacknowledged edits on a server crash. Provider events, store configuration.

  1. Client tracks an observed-document revision counter that advances on every Y.Doc change, including remote changes and deletions.
  2. At a bounded idle interval, explicit Save, or navigation boundary, capture a full binary Yjs state and a unique checkpoint_id with that observed counter. A state vector alone is not a sufficient saved-state proof for deletion-only changes.
  3. The room coordinator serializes the request, merges/validates it, captures immutable binary and commits a new PostgreSQL durable_revision.
  4. Only after commit, return a receipt bound to that checkpoint_id, document/generation, durable revision and stored-byte digest.
  5. Display Saved only if the client's observed counter has not changed since capture. Otherwise retain Saving and checkpoint again. A busy room may remain Saving conservatively; do not mislabel it.

Every writer uses the same queue: automatic onStore saves and explicit checkpoints share one per-document persistence coordinator. SQL expected-revision compare-and-swap plus retry/merge prevents delayed autosaves from replacing a newer committed state. Capture bytes before awaiting I/O; later edits stay dirty. Duplicate checkpoint requests return idempotent receipts. This is a custom Hocuspocus extension using supported custom-message/hooks, not a stock feature already proven to meet this contract. A compatibility/fault-injection prototype is an implementation gate. Hocuspocus hooks.

Commit state, revision and receipt atomically, and define PostgreSQL commit/backup durability in the operations policy. A normal coalescing interval does not bound outage delay: cap pending bytes, frame sizes, logical source and encoded CRDT state. If storage/backpressure limits are reached, stop accepting further live writes and offer visible recovery/export. Run the collaboration process with resource limits. An expired receipt retry resends/merges full state and receives a new receipt; unknown receipt is not proof of save or loss. Preserve validated provenance referenced by retained submissions when pruning receipts.

Start with the latest durable binary state, bounded receipt records and named immutable revisions. A per-delta durable journal is a later option if requirements demand stronger recovery of unacknowledged changes or measurements justify it; it is not required to turn the entire app into an event-sourced system. Current-state updates do not imply retaining a full snapshot every two seconds forever.

Offline recovery: account/project-scoped IndexedDB may retain pending CRDT work, with an explicit shared-device policy and logout cleanup/export. Local recovery is not server durability, and previously downloaded source cannot be retroactively unread after revocation. DB failure means no Saved receipt; queued/local recovery remains visible. An offline local Run may still work; a submission cannot be reported saved until the API transaction commits.

6.3 Awareness, chat and scaling

Bind awareness client IDs to the admitted connection; validate cursor ranges and stamp identity/display name from server-approved profile data. Do not trust claimed user IDs or expose email by default. Track connection leases individually and aggregate users, so closing one tab does not erase another tab's presence. Awareness is transient, separate from source persistence. Yjs awareness.

Persist a chat message and outbox event first, then broadcast its stable ID, UTC timestamp and body. The sender reconciles a pending bubble by client_message_id; reconnect fetches history after a cursor and deduplicates events. A channel group is notification delivery, not durable message storage: Channels can drop messages under capacity pressure. Channels delivery semantics.

One collaboration owner/instance is deliberate in v1. Later introduce document-affinity routing, ownership leases/fencing and measured sharding. The Hocuspocus Redis extension replicates/fans out messages; it is neither persistent storage nor automatic CPU sharding. Redis extension limitations. Scale the API independently, but do not enable multiple state writers until split-brain/recovery tests pass.

Version product-event envelopes with event_id, type, scope, server timestamp and aggregate version. Treat duplicate events and missing notifications as normal recoverable conditions. On reconnect refresh authoritative metadata/history rather than trusting a socket event stream to be complete.

7. Python execution and immutable source

7.1 Browser practice execution

Use a small runner application on a different registrable domain, embedded in the main UI through a restricted iframe; it creates a dedicated Pyodide Worker. Example placeholders: app.codealong.example versus run.codealong-lab.example. The authenticated app and runner must not share cookie scope, app storage or API privileges. Worker separation keeps Python CPU work off React; origin/capability separation protects app authority.

The iframe may require allow-scripts and allow-same-origin for practical Worker/assets support. Use that combination only across the separate runner origin, not for a same-origin app frame. Verify exact cross-origin-isolation/Permissions Policy behavior in supported browsers; do not assume it from top-level headers. Iframe sandbox behavior.

A trusted runner supervisor owns the Worker handle, timers and output budget. The app and runner use an origin/source-checked handshake and private MessageChannel. Messages are versioned and bound to a session nonce and run_id; declared operations are run, stdin, cancel, stdout/stderr, plot and terminal result. The runner has no generic parent/API-command bridge. Cross-origin messaging.

Run source: capture an immutable RunManifest containing the client's observed file list/normalized paths, exact UTF-8 source bytes, document generations, entrypoint, stdin mode and metadata version. Copy all source values from authoritative document models in one synchronous main-thread turn before any await, then hash those immutable bytes. Version the serialization/hash format; reject invalid encoding rather than silently changing source. Runtime identity includes engine, Python version and resolved package/profile digest. Do not read rendered editor DOM or keep reading the changing Y.Doc during execution. If remote edits arrive, show that output belongs to an earlier source snapshot. Offline Run is allowed only for a complete cached project or explicit local draft; never silently omit missing files.

Run lifecycle: initializing → ready → running → waiting_for_input → running → succeeded / failed / cancelled / timed_out. Exactly one terminal result per run_id; ignore late output from replaced/cancelled runs. Default to fresh interpreter/workspace state per run for reproducibility, accepting initialization cost; a warm isolated worker/runtime pool may optimize startup without retaining user globals across runs.

Use sequenced stdout/stderr chunks, bounded buffering and logical-line coalescing. Render safe text/constrained ANSI spans and bounded raster plots, not arbitrary HTML/SVG. This directly addresses the observed chunked console behavior. Scientific packages are opt-in reviewed profiles; self-host the pinned runtime/wheels and verify hashes. No unrestricted micropip installation or arbitrary network access in the first release.

Apply network restrictions to the Worker's own response CSP as well as the iframe shell. Allowed runtime-asset endpoints cannot proxy arbitrary URLs. The trusted supervisor relays only validated output data; it does not pass the app's MessagePort or credentials into Python. Python can forge practice output/terminal events through its JavaScript environment, so these remain untrusted feedback even when presented in the learning UI.

Interactive input uses a capability-tested stdin bridge, preferably SAB/Atomics when isolation headers work. Provide declared batch stdin when interactive capability is unavailable; avoid coupling it to an app-wide service worker. Soft interrupt is cooperative and may be caught; the supervisor terminates and recreates the Worker after a short grace/deadline. Pyodide documents the Worker/SAB requirements for interrupts. Pyodide interruption, standard streams.

Proposed starting budgets: 20 bounded text files per small project, 128 KiB source per file, 30 seconds preview wall time, 1 MiB retained console output and bounded plot/virtual-file sizes. Runtime profiles can adjust these after tests. Browser execution does not provide a reliable hard per-run memory quota; malicious code can still exhaust its browser resources. These budgets are product controls to validate, not security/capacity guarantees.

7.2 Exact submissions and visible checks

Visible checks run against a frozen source/runtime snapshot and provide learning feedback. They are inspectable and editable by the learner, so they cannot establish an authoritative score.

Submit the source the learner chose: offer Submit tested version H versus Submit current code H2. Upload the exact captured manifest, validate its project/file/generation/assignment scope, normalized paths and quotas, and recompute hashes on the server. Recheck access, assignment version, eligibility and deadline at commit; server time governs timeliness. Reserve attempt/storage/job budgets atomically and use a user/assignment-scoped idempotency key. For bounded text, commit immutable ProjectRevision/RevisionFile plus Submission/participants/outbox in one transaction. Link a preceding practice run by the same manifest hash. A changed live room cannot silently substitute different peer edits after the learner clicks Submit; stale structural/authorization changes cause an explicit retry/error. This is untrusted learner source accepted for evaluation, not a trusted claim that it is the latest global shared state.

Record provenance as client-submitted snapshot versus shared-room checkpoint. Store client submissions as submission-owned immutable artifacts linked to the source project; they do not modify live code or appear in shared project history merely because a learner has submission eligibility. Creating a shared named project revision requires that separate project permission. Collaboration receipts are provenance only, not proof that submitted bytes equal a checkpoint or establish authorship.

Submission artifact access derives from frozen participants and authorized assignment teaching roles, not source-project ownership/read grants. Apply this to revision/file downloads and signed artifact URLs; ordinary project shares cannot publish private submission snapshots. Validate every participant from authoritative assignment enrollment/team policy and freeze that list in the transaction. A viewer, editor or instructor mentor is not automatically a graded teammate, and clients cannot nominate arbitrary users.

For a named shared-room revision, the coordinator must freeze/copy the requested file payloads and metadata while creating it and retain them until the revision transaction commits. Latest DocumentState plus an old receipt cannot reconstruct an old checkpoint. Define the multi-file capture boundary explicitly; do not claim that unrelated file receipts form one instantaneous global state. Large object-store uploads must be staged/hashed before the database transaction references them; garbage-collect orphan uploads. Hash-based deduplication never authorizes access to someone else's blob. Display the accepted immutable revision/hash and allow viewing that source after submission.

7.3 Later authoritative server assessment

When hidden tests or non-WASM capabilities are required, add a separate Linux execution plane. The API creates a job for an immutable revision/test-suite/runtime version; a trusted controller obtains narrowly scoped artifacts and starts disposable CPython sandboxes. Django, collaboration and ordinary Celery application workers never run learner code.

Use gVisor runsc on dedicated runner hosts as the first practical extra isolation boundary, with strict external CPU/memory/PID/wall-time/output/scratch controls, a read-only root, no network, no host mounts/Docker socket/capabilities/app credentials and cleanup on every terminal path. A container alone is not a sufficient design for arbitrary hostile Python. gVisor adds defense but does not replace host/resource/network policy. gVisor security model.

Start assessment with black-box stdin/stdout tasks: the trusted controller keeps expected outputs/scoring outside the submission sandbox. Hidden inputs necessarily reach submitted code; hidden test files in the same Python process are not reliably secret from it. Function/pytest grading needs a separately documented tampering/disclosure model. Never trust student-emitted passed=true as a grade. A verified result also does not prove individual authorship in collaborative work.

A native CPython grade does not automatically reproduce Pyodide behavior even with identical source. Align supported Python/packages where practical, show the grading runtime explicitly and test browser/native compatibility. Results always identify their immutable source, engine and assessment version.

Firecracker is an optional later VM-isolation alternative when requirements and Linux/KVM operations justify it, not a compulsory first-release dependency. Firecracker production requirements.

8. Authentication and authorization

Browser v1: prefer Django server-side sessions with Secure, HttpOnly, host-only cookies, same-origin reverse-proxied APIs and CSRF protection. Use established framework flows for email verification, password reset and optional Google/OIDC; validate issuer/audience/nonce/state and local account status. Avoid a hand-written access/refresh JWT lifecycle in browser storage. Mobile/external API tokens can be introduced when there is an actual client requirement. Django sessions.

Two permission scopes: workspace owner/instructor/learner govern membership and teaching; project owner/editor/viewer govern live project content. Instructor status permits authoring assignments and reading submitted snapshots in scope, not blanket access to every private live project. Explicit grants enable mentoring/teaching access. Platform operators use audited administrative access.

ActionProject ownerEditorViewerInstructor role alone
Read project / run local copyYesYesYesOnly if project access is granted.
Edit source/file treeYesYesNoNo implicit live-code access.
Manage grants/archive projectYesNoNoOnly with explicit management authority.
Submit individual/team assignmentRequires permitted assignment participation and submission policy; viewer access alone is insufficient.No implicit learner submission authority.
Author assignment / review submitted workProject ownership alone gives no teaching privilege.Yes, within the authorized workspace/assignment.

Centralize named actions and relationship checks, deny by default and scope queries before fetching objects. This applies to REST, tickets, live writes, exports, revisions, chat history, shared links and grading artifacts. Never authorize an arbitrary project by checking membership in a separately supplied group ID. OWASP authorization guidance.

Live access: opaque, one-use admission tickets expire quickly (proposed 30 seconds) and never appear in query strings. Session/ACL versions accompany renewable project leases. Logout/revocation sends invalidation events and forces reauthorization; lease expiry provides a tested bounded fallback if notification is lost. A proposed 30-second maximum stale-authorization window must be validated and accepted; Redis Pub/Sub alone is not instantaneous revocation. Fail closed when a lease cannot be renewed.

Invitations and shares store token digests, scope, expiry, revocation and optional recipient/usage limits. Public snapshot viewers can receive minimal read-only access to that immutable revision; live editing requires an account in v1. Restoring history initially means creating a new copy, avoiding destructive overwrites of active collaborators; a later replace-current workflow must change generation and handle offline edits explicitly.

9. Security and privacy boundaries

ThreatArchitectural control and reason
Python reaches application authorityDifferent runner site, credential-free messages, separate CSP on shell and Worker, reviewed asset-only network destinations and no authenticated API proxy. Pyodide's JS bridge makes Python import restrictions alone insufficient.
Infinite loop / resource exhaustionSupervisor outside Worker, hard termination fallback, output/files/plot caps. Server grading additionally requires external OS-level budgets and queue quotas. Browser memory remains a residual risk.
Hidden test leakage or falsified gradesNever ship hidden suites/keys to browser or live project files. Trusted external controller owns comparison/scoring; filter feedback; record runtime and test versions.
Cross-tenant / forged identifiersScoped policy checks, invariant constraints, permission-matrix tests, least-privilege service roles and audited grant changes.
Socket misuse / impersonationOrigin validation, narrow admission, awareness identity binding, read-only enforcement, rate/size/structure limits and lease revocation.
XSS / unsafe artifactsReact text rendering, constrained ANSI spans, sanitized author Markdown, bounded raster plot output, safe download content types. No arbitrary learner HTML/SVG execution in the app origin.
Credential leakageNo session/auth tokens in URLs, no broad Domain cookies, log redaction, secret manager/env injection and context-appropriate .dockerignore. Do not bake .env into images.
Shared-device data exposureExplicit local recovery policy, account-scoped storage and logout handling; no shared cache of authenticated API bodies. Minimize collaborator profile data and define source/chat/submission retention.
Deployment data lossDrain and checkpoint, revision/CAS discipline, idempotent outbox/jobs, PostgreSQL backups and restore drills; no blanket Redis flush or unverified saved indicator.
Supply-chain / runtime driftLockfiles, runtime/image digests, reviewed wheels/assets, patch upgrades and integration/security regression tests.

No execution boundary is absolute. The first-release promise is limited browser preview with constrained app privileges; authoritative execution stays disabled until isolated hosts, budgets, cleanup and threat-model tests pass. Select retention, regional hosting and school/minor privacy requirements before any institutional deployment rather than assuming self-hosting alone establishes compliance.
