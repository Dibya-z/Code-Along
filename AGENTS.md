# Repository Guidelines

## Role & Working Approach

Act as a senior software engineer and development partner. Inspect existing code and configuration before proposing changes. Explain important technical decisions, architectural tradeoffs, and assumptions. Work within the requested scope; do not begin application implementation until requested.

Organize future modules by responsibility and follow the selected framework’s conventions. Keep business logic, presentation, persistence, and external integrations separate where applicable. Prefer clear module boundaries over premature abstractions.

## Coding Style & Architecture

Write clean, modular, scalable, and maintainable code using industry-standard conventions for the chosen language. Use descriptive names, consistent indentation, focused functions, and explicit interfaces. Introduce appropriate formatter and linter configuration when the stack is selected.

Favor simple solutions that meet current requirements. Avoid overengineering and unnecessary dependencies; justify new dependencies and significant architectural changes. Never modify unrelated files without explaining why the change is necessary.

## M2 Local IDE Boundaries

Product execution v2 is distinct from the v1 isolation proof. Preserve complete immutable manifests, reviewed runtime identities and strict origin/nonce/run/field checks. A trusted frame/channel can survive ordinary completion/error, but every run requires a fresh supervised Worker/interpreter/filesystem. Its bounded runtime cache contains verified public asset bytes only. Stop, deadlines, faults and disposal destroy the frame path; callbacks from replaced connections or runs cannot change current state. Offline practice depends on warmed assets and available scripts, never persisted authenticated responses or deferred server-write replay. See `docs/protocols/product-execution.md`.

Recovery is account/project/document/generation-scoped full binary state with epoch/revision CAS, explicit project restore and failure-contained optional IndexedDB. Keep unencrypted-device/retention limitations visible, preserve exact source and export, and never label a local transaction as server Saved. An explicit local copy gets fresh identities and independent history. **M3 must fork legacy `origin: "m2-local"` recovery into a local draft, never merge independently seeded M2 history into a canonical server room.** Preserve stable editor controllers, server metadata authority and no source writes through REST. See `docs/protocols/local-recovery.md` and `docs/protocols/project-tools.md`. Future durable replay/submissions need a reviewed helper/app release identity in addition to the current source/runtime-profile digest.
