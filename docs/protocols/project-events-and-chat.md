# Project events and durable chat

M3 implementation is undergoing integration gates; completed evidence belongs in the [M3 validation record](../architecture/m3-validation.md). Product notifications use Django Channels at `/events`; source and cursors remain on the separate [Yjs collaboration channel](product-collaboration.md). Redis is transport, not a chat/event database. Learner Python never runs in a notification task.

## Durable mutations and delivery

Each project has a PostgreSQL bigint event head. `events.services.emit_project_event` requires the caller's workspace → project transaction, increments that head and inserts an `OutboxEvent` with the domain mutation. Every public envelope has `code-along.events` version 1, a stable event UUID, project UUID, decimal-string sequence, type, server UTC time and bounded typed data. Metadata/access/revision events contain version or revision identities rather than source, credentials or private share identifiers. Chat events retain a message pointer internally; dispatch/replay projects the committed safe message DTO.

`InvalidationDelivery` is a separate private ledger for at most 128 lease UUIDs and an optional hashed session group. It has no session/lease foreign key: logout may remove session and lease rows while their invalidation still needs retry. Private delivery never appears in public replay or envelopes. Lease revocation and enqueue commit together; fast best-effort invalidation and fail-closed lease expiry remain complementary protections.

`events.dispatcher.dispatch_batch` fairly claims at most eight rows across the public/private queues using `SELECT FOR UPDATE SKIP LOCKED`. Its UUID claim and 30-second expiry commit before network I/O. Channel publication has a two-second timeout; private Node control has a 250 ms timeout. Completion/retry uses the still-owned, unexpired claim, so an old publisher cannot clear a replacement claim. Retry backoff is bounded at 60 seconds, counters saturate, and diagnostics contain bounded codes rather than payloads or driver exceptions. Interrupted claims become eligible again. A crash after publication can repeat the **same** event ID; published means broker acceptance, not that a learner received or read it.

The exact pinned Celery task `code_along.events.dispatch_outbox` accepts no arguments and runs one finite dispatch batch. A best-effort post-commit wake improves latency; the separate scheduler polls every two seconds to repair a missed wake or broker downtime. Its short-lived wake messages may expire because the durable work remains in PostgreSQL. The same trusted worker runs a separate finite [receipt-retention task](product-collaboration.md#bounded-receipt-retention) every 15 seconds. Tasks accept JSON, ignore results and disable worker remote control. There is no implicit AMQP or in-memory production fallback.

Development uses one solo worker and one explicitly owned scheduler, both from the existing API image. Celery's embedded scheduler also forks a process; separate direct ownership makes forced fixture shutdown predictable. Compose caps their CPU/memory, drops capabilities, keeps their root filesystems read only and uses ephemeral scheduler storage. No additional VM, mail mount or persistent queue volume is introduced. Queue Redis database 2 and its key prefix are separate from coordination database 0. Explicit TLS broker URLs retain certificate/hostname verification. These development settings do not certify production job operations or load.

## Subscription and repair

The socket accepts only the exact app Origin/path, the actual framework session and a verified active account. One strict subscribe command chooses an ordinary authorized project. Live source links grant no event or chat authority. Channels joins the project group before establishing the authoritative replay head; the client buffers bootstrap notifications while refreshing its REST snapshots.

The server rechecks the actual session/auth hash, account, workspace membership and ordinary project access before forwarding an event and every ten seconds. Authorization has a conservative 30-second deadline; unavailable checks close fail-closed. Private logout notifications close the session's sockets promptly. Client messages cannot mutate source, metadata or chat.

The subscribed response either includes a complete bounded replay (at most ten events) or requires authoritative refresh. `GET /api/v1/projects/{project}/events/?after=…&limit=…` reads committed retained rows, including undispatched ones, with at most 100 per page. Missing/pruned/future cursors request refresh. Duplicate/out-of-order event IDs/sequences are tolerated. A periodic authenticated head exposes a dropped **last** notification even if no later event arrives. Reconnect, cursor gaps and head differences repair through REST, without treating Channels as durable delivery. Source keystrokes do not generate these metadata events.

## Persisted chat

`POST /api/v1/projects/{project}/chat/messages/` requires a current verified session, CSRF, ordinary owner/editor access and an open workspace/project. It accepts only plaintext body and `client_message_id`, validates exact UTF-8/nonblank/no NUL/at most 4096 bytes, and commits `ChatMessage` and its event together. Nonblank uses a fixed shared 30-codepoint whitespace set, including FEFF and the Python/JavaScript whitespace differences; accepted text is preserved exactly. The server supplies UTC time and sequence. Unique `(author, client_message_id)` makes identical retries return the original record; reusing that identity with a different project/body conflicts without exposing the other record. Each project currently permits 10,000 messages and 32 MiB of retained message bytes. There is no automatic destructive chat pruning.

Ordinary viewers may read history but cannot post. Snapshot/live source capabilities grant neither. History uses exclusive `before`/`after` cursors with bounded pages and ascending results; chat cursors can have gaps because other project events share the sequence. Deleted projections preserve ID/cursor with no body; moderation controls are outside this milestone.

The account/project-scoped Discussion UI renders text, labels message times from server UTC and loads older history explicitly. Pending sends keep their frozen nonce/body. HTTP response, event or history proof reconciles by stable message ID and `(author ID, client nonce)`; different authors may use the same nonce. A late failed HTTP response cannot downgrade a message already proven committed. An uncertain send says **Not confirmed**, preserving a manual same-request retry after fresh authorization. Offline/reconnect never automatically replays a server mutation. Signing out or changing account/project destroys subscriptions and invalidates callbacks; the next controller starts with fresh state. Chat is not written to device recovery. Reading older messages preserves the scroll anchor, and incoming unread messages have an explicit Jump to latest action.

## Operational limits

Single-instance collaboration ownership, bounded queues/frames and conservative quotas remain explicit. The outbox retains pending work through broker/process failure but does not promise zero-delay or exactly-once notification delivery. Basic receipt bounds are enforced in M3; M5 retains measured classroom capacity, broader ledger/artifact/chat retention, backup/restore, metrics/alerts, complete accessibility/security review and deployment readiness. Do not treat durable user history/chat/receipts as workstation cache cleanup.
