# Product Python execution v2

M2 uses a product manifest separate from the M0 v1 runner proof. Both contracts share the supervised Worker engine; the v1 proof wire format stays unchanged.

`packages/contracts/execution/project-manifest.ts` owns v2 capture and validation. A manifest contains `version: 2`, project identity, `source_kind` (`project` or explicit `local_draft`), the observed metadata version, entrypoint file identity, reviewed runtime identity, stdin mode, every file and the aggregate SHA-256 digest. Each file includes its file/document IDs, generation, exact path/source and source SHA-256. Runtime identity includes the engine/version, Python version and immutable reviewed asset/profile inventory digest. It grants no application authority and is not an authentication or grading claim.

All live values are copied synchronously from authoritative editor documents before the first `await`. Hashing reads only that private copy. Files sort by ASCII path; canonical JSON uses the fixed property order in `canonical()`, UTF-8 encoding and no whitespace. The aggregate hashes the complete canonical manifest excluding its own digest, including exact source strings and their hashes. CRLF, Unicode and final newlines are preserved. SHA-256 bytes render as lowercase hexadecimal. A verifier rejects unknown fields, noncanonical order, unreviewed runtime identities, source/digest changes and invalid file sets.

Limits match the product API: 1–20 Python files, 128 KiB UTF-8 per file, 1 MiB aggregate, relative ASCII module paths up to 160 characters, no traversal/NUL/unpaired surrogates, case-insensitive duplicate paths, duplicate file/document identities or module/folder import collisions. The entrypoint must exist. An editor cannot capture until every known file is loaded and verified; an explicit local draft is still subject to completeness and the same bounds. Offline recovery must supply a complete cached project rather than omitting unavailable files.

`EditorWorkspace.snapshotInput()` reads Y.Text and current reconciled metadata; editor DOM and React text mirrors are never execution inputs. `captureWorkspaceRun()` records the model revision with the immutable manifest. `isCurrentRun()` cheaply detects later source or metadata/runtime changes so output can be labeled as belonging to earlier source. A source revision is local provenance; it does not certify global room order, durable save status, authorship or trusted assessment.

## Iframe and Worker connection

The HTTPS proxy supplies an exact `runner-origin` meta value. Current development uses the different sites `127.0.0.1` and `localhost`; another port on the application hostname is rejected. Production host/site, TLS and cookie policy still need the deployment gate; URL shape validation is not a public-suffix-list site validator.

The first product run opens a sandboxed iframe and private MessageChannel with a fresh UUID session nonce. Each run has a new UUID run ID. A workbench can retain the trusted connection after a shell-confirmed success or Python failure; the trusted shell has already terminated that run’s Worker before emitting its terminal event. Every new run still creates a fresh Worker, interpreter and filesystem. The application sends only `{protocol, version: 2, type: connect, session_nonce}` to the configured exact origin and transfers one port. The runner accepts one connection only from its configured parent origin/window. Its ready reply reports measured isolation/interactive capability. Commands/events are versioned, nonce/run-bound and field-exact; undeclared API, credential and fetch operations are rejected. Product commands carry only run manifests, bounded stdin, input and cancellation. Batch input is limited to 100 lines, 4 KiB each and 64 KiB total.

The shared trusted supervisor reserves a run before async verification, owns Worker handles and independent startup/wall timers, verifies source hashes, sequences/caps output and terminates on completion/error/Stop. The Worker receives source and stdin, never the parent's application port or credentials. Every run starts a fresh interpreter and virtual filesystem. Late events from old frames/Workers are ignored; result runtime/manifest identity must match capture. An additional parent deadline closes a lost iframe. Stop, deadlines, output/protocol/connection faults and disposal close the complete frame/port path. Connection-generation and run-ID checks reject callbacks from replaced sessions and earlier runs. The parent renews after 90 admitted attempts, before the shell’s 100-ID replay budget is exhausted. Route disposal releases private source/controller resources and the runner.

The app denies its own Workers; the separate runner shell and Worker have separate CSPs. The Worker's own response permits only self-hosted runtime assets and Wasm evaluation, with no child Worker or app/external network destination. The runner site has no authenticated API routing. Python can forge local feedback through its JavaScript environment, so run success remains untrusted practice feedback. Browser resource limits are soft product controls; no hard memory quota is claimed.

## Reviewed runtime profiles

Core and opt-in NumPy share the pinned Pyodide engine. The authenticated catalogue enables only compiled, reviewed identities; choosing a profile for a local run does not mutate the shared project default. The snapshot records the actual chosen inventory digest. `runtime-inventory.ts` bounds inventories/assets before buffering and verifies their canonical SHA-256. Build tooling admits only pinned official assets, verifies size/digest and emits content-addressed runner URLs. The Worker verifies the inventory/core assets, filters the package lock to the reviewed wheel set and confirms requested packages loaded before learner source. No arbitrary package installation is offered. Profile inventories, licensing and the deferred Matplotlib dependency review are documented in `packages/runtime-profiles/README.md`.

## Console and input

The application coalesces split writes into logical rows, bounds retained rows to 5,000 and renders at most 200 at once. Rows longer than 8,192 UTF-16 units split at code-point boundaries. A streaming constant-space decoder removes ANSI/OSC/control sequences; output and captured source render as React text. Stdout/stderr have text labels as well as colors. Paging and paused following preserve reading position. Clear affects display only, retaining the run sequence and cumulative 1 MiB byte budget.

Input mode is captured before execution. Interactive mode requires the measured embedded capability; an unavailable capability produces an explicit error directing the user to batch input. Input/EOF is accepted once while waiting; a 4 KiB UTF-8 line travels only through the private runner port/mailbox. The 30-second wall deadline includes time waiting for input. Batch limits remain 100 lines/64 KiB total.

## Bounded raster output

Product v2 adds `plot` events with `index`, `title` and `png: Uint8Array`; their independent zero-based index does not consume stdout/stderr sequence numbers. Old v2 clients may ignore this additive event. The v1 adapter emits no plot events. Each boundary validates a restricted PNG subset: signature, chunk bounds/CRC, 8-bit RGB/RGBA, IHDR/IDAT/IEND only, no animation/metadata/interlace, at most 1600×1200/1,920,000 pixels. Limits are four plots, 512 KiB each and 2 MiB total; titles are at most 160 UTF-8 bytes and always text. The app renders validated PNG blobs under `img-src blob:` only; frames/scripts/workers retain their existing policies. Object URLs are revoked on replacement/unmount. Downloads are PNG files.

Every product Worker installs the original `code_along` helper after runtime setup. `plot(values, title="Line plot")` draws 2–1,000 finite numeric samples on a 640×360 canvas, ordered left to right with automatic vertical scaling. `display_png(bytes, title="Plot")` submits an existing restricted PNG. Example: `from code_along import plot; plot([1, 4, 2, 7], title="My samples")`. This is a small practice helper, not Matplotlib or an arbitrary rich-output renderer. A project module with the same name follows ordinary Python path precedence.

## Supervision and resource budgets

Worker output batches into at most 4,096 UTF-16-unit chunks, preserving code points and stream order. It flushes before input/plots, periodically on live lines, and at success/error. Python streams also flush in a supervised `finally` block, so unterminated output is admitted and counted. A byte-at-a-time flood cannot create one application message per byte. The trusted shell and parent separately enforce 4,096 output events and the cumulative 1 MiB byte cap; Worker limits are supplemental. Exactly one terminal result wins, and late/replaced Worker messages are ignored.

After trusted runtime/project setup, pinned MEMFS `mknod`, `write` and `doTruncate` hooks enforce 8 MiB cumulative positive regular-file growth, 64 successful new regular files, 128 new nodes and 1,024-character virtual paths. Append/sparse/truncate growth is checked before the ordinary operation; failed operations do not consume creation quota, and shrinking/deleting does not replenish it. Guard rejection reports a bounded virtual-file explanation and raises the runtime ENOSPC error. These hooks cover ordinary Python filesystem operations, not every possible JavaScript/MEMFS escape or memory allocation. Learner code can alter its own Worker APIs; this is a soft product budget, never a hard storage/RAM/security sandbox claim. Time/output/plot supervision remains outside the Worker. Stop destroys the active frame/Worker path; the next run has a new interpreter/filesystem.

## Warmed offline practice

An already open, previously verified session can run a complete cached project or explicit local draft using its retained trusted connection and previously loaded runtime assets. Runs capture every file and keep the same source, profile, input and resource checks. Each attempt uses a fresh Worker and Python state, including after an ordinary Python exception; fixing a program error does not require reusing its interpreter. Missing project files keep Run disabled. No service worker, authenticated-response cache, persisted login state or alternate server execution path is introduced.

The trusted frame also holds up to two complete reviewed public runtime bundles, bounded to 64 MiB combined. A Worker can offer one bundle before it starts learner code. Admission copies non-shared bytes before awaiting hashes, verifies the compiled inventory digest and every exact asset size/SHA-256, and rejects unknown, partial or duplicate sets. These internal messages never reach the app port. Frame disposal clears entries and prevents pending validation from repopulating them.

A fresh Worker receives independent byte copies and verifies them again. Its narrow fetch adapter supplies only exact reviewed asset URLs, including Wasm, stdlib and wheels, from those bytes; other requests retain the ordinary response CSP/network behavior. Small module/Worker scripts still use the browser's HTTPS cache. No interpreter, filesystem, learner source, credentials or output enters the frame cache. This avoids relying on a browser retaining a large Wasm response, while keeping a new Worker and Python state for every run.

Browser script caching remains conditional: a missing/evicted asset, newly selected environment, invalid/untrusted TLS, page refresh/navigation, Stop or session renewal can require a network connection. Cold offline installation/login is not provided. The UI identifies offline practice and never reports server Saved or current server authorization from cached data. An explicit authenticated denial still removes the signed-in view; a connection failure can retain the previously verified in-memory view. Backend authorization continues on every API request. Server mutations use `networkMode: 'always'` with no retries, so an offline file/workspace action fails immediately rather than being queued for reconnect or a later account.

The original ephemeral HTTPS-error fixtures cannot establish offline cache support. Separate static HTTP/HTTPS experiments reproduced Chromium rejecting certificate-error responses from cache and WebKit retaining small fetch responses only in a persistent test data store. The full product gate then exposed WebKit not retaining the large Wasm response; the bounded verified frame cache addresses that data-asset gap. The offline product fixture therefore creates a fresh private temporary profile, pins only the fixture certificate’s public key in the Chromium process, uses WebKit’s isolated TLS exception and removes the profile afterwards. OS certificate trust and the owner’s browser profile are untouched. Service workers are explicitly blocked in these tests. This verifies the tested browser/cache configuration, not every private/retail/mobile mode or the owner’s deferred local trust setup.

Primary background: [Chromium HTTP cache certificate-error handling](https://chromium.googlesource.com/chromium/src/+/d2875522f7d19b4c084e0ced310d220564c029ae/net/http/http_cache_transaction.cc), [Playwright context offline emulation](https://playwright.dev/docs/api/class-browsercontext#browser-context-set-offline), and [Playwright maintainer explanation of cache-dependent offline behavior](https://github.com/microsoft/playwright/issues/29360). Actual product evidence is recorded in the M2 validation report.
